# 制作・引継ぎ手順 v1.2.0（ハーネス版）

共通基準1.0.0、配布仕様1.2.0。S001（人手中心）・S002（多エージェント検証、累積約2,700万トークン。うち9割超が検証用サブエージェント）の制作で得た知見を `scripts/harness.py` と参照文書（format-spec、quality-checklist、examples、source-registry）に固定し、1件を「一度読む・一度書く」だけで同じ品質に達することを狙う。品質は「lintで機械確認できる整合性」＋「独立解答で確認する解答可能性」＋「チェックリストで確認する内容品質」＋「レジストリで確認済みの法令事実の再利用」で担保する。

## 0. 読む・書くの原則

- 読むのは、SKILL.md、production-standard、output-contract、format-spec、quality-checklist、本書、examples、`_context.json`、`_sources.json`。原典スナップショット全文・完成例全文・`source-registry.json` 本体・自分が書いたファイルの全文は読まない。
- 書くのは、`_spec.json`（≈3〜5k字）と4本のMarkdown（各1回のWrite。3万字を超える見込みなら前半・後半の2回に分ける）。修正は Edit の差分。curriculum.json と骨組みは生成する。
- サブエージェント・Workflow・Web検索・多視点レビューは、4節の独立解答（1エージェント1回）を除き、ユーザーが明示的に依頼した場合だけ使う。
- 予算の単位と目安は SKILL.md「予算」。累積トークン（Claude Codeの表示）は次の制作で実測し、ここに記録する：未計測。

## 1. plan

```
python scripts/harness.py plan Sxxx --source SOURCE.json --out OUT_DIR --catalog CATALOG.json
```
出力：`_context.json`（対象スキル行、関連スキル定義、関連タスク、ロール、当該スキルのタスク×スキル行。法令を含む場合だけ12シート判定項目（根拠ID付き）・Tier・24シートの原典記載行）、`_sources.json`（一致した registry entry の本文：facts_text・cards・scope・not_covered・unverified・urls・origin・events・stale理由。hints＝関連タスクの記述にだけ一致した entry。unregistered＝entry のない話題）、`_spec.template.json`、手順。台帳が draft-reviewed 以上で成果物があれば何も書かずに拒否する（`--force` で改訂）。

ここで「本講座が担うこと」「前提として説明すること」「他スキルに委ねること」を各1〜3文で決め、spec の `scope` に書く（関連スキルの定義は `_context.json` にある）。

## 2. spec → build

`_spec.template.json` を `_spec.json` にコピーして埋める。

- 目標：原典の動詞ごとに分割（Lv3は共通定義の「設計・指導・例外判断」を含む）。各目標に条件・入力・提出物・品質・境界・典型失敗（制作基準の7項目）を書く。ここで書いた境界と典型失敗が、評価の重大誤判断と1点例の根拠になる。
- 単元：目標ごとに1つ＋各Lv末に一巡・評価単元。分数は実行量から積み上げる（S001・S002の値を機械的に流用しない）。
- 評価：観点名（04採点表の行名になる）・提出物・合格条件・重大誤判断（観察可能な行動で）。
- roles（原典06シートのIDと架空の担当）、templates（様式IDと列）、cards（抜粋カードIDと registry entry）。03・04・02・01 で同じIDを使うための割付を先に決める。

```
python scripts/harness.py build --spec OUT_DIR/_spec.json --source SOURCE.json --out OUT_DIR
```
build は構造の不備（未割付の目標、Lv不一致、評価分0、観点なし等）を全件列挙して止まる。通れば `curriculum.json` と `_tables.md`（01の単元表・目標表・範囲・合格基準、02の見出し行、03の役割表・様式見出し・カード見出し、04の§2見出しと§8自己点検表の骨組み）が生成される。

## 3. 一次資料の扱い

- `_sources.json` の `cards` は S002 で一次資料と照合済みの抜粋カード本文。K カードにはこれを転記し、`（registry: entry-id）`、確認日、版、原典との差（`origin` の原典記載と比較）を書く。`facts_text` は要約なので、カードに書くときは条番号と趣旨に留め、原文の再現を装わない。
- `scope` 外・`not_covered` の条文が教材の中核なら、entry の `urls` に対して `harness.py fetch URL --out DIR --grep "第二十七条"` のように条名・条番号で絞って該当箇所だけ読む（一般語で grep しない。既定で30件・前後200字）。読まない場合は「未確認」と書く。
- stale（`stale_reasons`：120日超、または `events` の期日到来）でも制作は止めない。確認日付きで転記し、01 §2 の表と台帳 `open_items` に「確認日以降の改正は未反映・再確認事項」を書く。レジストリの一括再確認は制作と分けて行う（7節）。
- `unregistered`（entry も URL もない話題）と `unverified`（二次資料由来）は「未確認・要法務確認（根拠：…）」と書き、確定事実として教えない。新規の一次資料取得はユーザーが依頼した場合のみ。
- fetch が `FETCH FAILED`（WAF・索引ページ・SPA）を返したら：ブラウザペインでURLを開き、`javascript_tool` で `document.body.innerText` から必要な見出しの前後（1条ずつ）を切り出して、案内されたファイル名で保存し、`--grep-only --grep 語` で読む。統合版全文をコンテキストに貼らない。

## 4. 書く順序と検査

03（役割表→練習ケースと演習→様式→A1〜A3→付録K）→04（§2 全演習の模範解→応答カード→採点表→§8の骨組み）→02（用語集→単元本文）→01（_tables.md の表を貼り、原典対応・一次資料表・範囲・実施方法）。評価と模範解を先に決めてから本文を書く（制作基準3・4）。04 §2 の見出しは `_tables.md` の `### Exx` を全部使う（lint が照合）。

ケースは練習P（解説済み）と評価Q/R（初見）を分け、各ケースに概要表・既存記録（日付付き）・事象カード・応答カードを付ける。日付を扱うケースは `### 日付計算表`（format-spec）を置き、lint に再計算させる。法令を扱う場合、当てはめは「候補・暫定・要法務判定」で書き、確定者と通知の実施者を役割表で分ける。

```
python scripts/harness.py lint OUT_DIR --source SOURCE.json
```
エラー（時間・目標・演習の不一致、未定義ID、観点名の不一致、模範解見出し欠落、応答カード欠落、日付計算の不一致、URLなし、骨組みの「記入」残り、§8未記入）は差分編集で直す。警告は自己点検の該当項目と合わせて 04 §8 の根拠欄に書く。

独立解答：Agent が使える環境では、03-exercises.md だけを渡し「A1〜A3 を資料だけで解き、解けない設問・不足事実・矛盾を列挙する」1エージェントを1回起動し、返答を 04 の模範解・応答カードと突き合わせて直す（≈5〜7万トークン。S002 で最も多くの欠陥を見つけた検証）。使えない環境では自分で解き直し、04 §8 の項目27に「独立解答は未実施（自己解答のみ）」と書く。

自己点検：quality-checklist の28項目を、`_tables.md` の §8 骨組みに「済／該当なし／未実施（理由）」と確認方法・根拠で埋める（済には根拠必須。lint が検査）。

```
python scripts/harness.py finish OUT_DIR --source SOURCE.json --catalog CATALOG.json
```
lint が通り §8 が完全なら、curriculum.json に自己点検日を記録し、台帳の当該行だけを更新（validation、self_check、使った registry entry と確認日、付録URL、open_items）して作業ファイルを消す。`--force` はエラーを残したまま status を `draft-unverified` として記録する（完成扱いにしない）。報告は「作成物／実施した確認（lint・独立解答・registry再利用・再取得した資料）／未確認・未実施（試行授業、採点者間確認、実務認定、法令の当てはめ、未実施の点検項目）」の3点。

## 5. 大量制作

複数IDは1件ずつ plan→finish を完結させ、次へ進む。文脈が長くなったら、対象ID・完了ファイル・未解決事項・次の作業を台帳の `open_items` に残して再開する。並列化はユーザーが要求した場合に限り、保存先をID別に分ける。

## 6. レジストリの保守（制作とは別の作業）

- 一括再確認：`maintained_at` から120日ごと、または `events` の期日到来時に、entry 単位で一次資料を再取得して facts・cards を更新し、`checked_at` と `maintained_at` を更新する。再確認していない entry の `checked_at` は動かさない。
- 新しい法令事実を制作中に一次資料で確認したら、該当 entry の facts に追記し、その entry の `checked_at` を更新する（他 entry は触らない）。二次資料しか確認できないものは `unverified` に置く。反証された事実は削除し notes に理由を残す。
- 影響範囲：facts を変えたら、台帳の `sources.registry` に同じ entry を持つ教材を列挙し、未改訂として台帳に明記する。

## 7. S001・S002で確定した点検方法（チェックリストの根拠）

- 数値は独立に再計算（支出と未払い発注の重複、率の分母、期限の逆算と起算日）。日付は日付計算表で lint に検算させる。
- 正常なケースを不必要に停止させない。異常検出だけの採点にしない。有効な判定は変更トリガーに該当する範囲だけ再判定へ回す。
- 審査前の判断案を実承認として記入しない。受講者が適用法や公開可否を確定した扱いにしない。
- 複数時点のケース間で未承認作業の実施を仮定しない。
- 指導は再提出を読んで改善・残件を判定するところまで含む。再提出カードは本人の文書として書く。
- 教材内の不足情報を「講師に聞く」で放置せず、応答カードを用意する。
- 法令は確認日付きで「現行」と「未施行の改正」を分け、個別の当てはめは断定しない。適用日と現在の義務を区別する。
- 模範解を先に書き、練習の模範解を評価の解答に転記しない（lint が25字以上の同一文を警告）。
